## 二、认证链路现状

```
浏览器
  └─ token 存 localStorage (gallery_token)
  └─ axios 请求拦截器自动加 Authorization: Bearer <token>
  └─ 401 响应拦截器 → logout + 跳 #/login
  └─ 路由守卫 (router/index.js) → meta.auth 页面未登录跳 /login  【纯前端，仅 UX】
        │
        ▼
后端 Express (server/index.js)
  ├─ requireAuth 中间件：验 Bearer + jwt.verify
  ├─ /api/auth/register | login | me
  ├─ /api/images | upload | categories  （全部挂 requireAuth，按 req.user.id 隔离）
  └─ /uploads 静态目录  【无鉴权，裸奔】
        │
        ▼
SQLite (server/db.js)
  └─ images.user_id / categories.user_id 全链路过滤 + 越权防护
```

## 三、做得好的（肯定）

- **多用户数据隔离扎实**：`images.user_id` / `categories.user_id` 全链路，`getImages`/`deleteImage`/`updateImageName`/`updateCategory`/`deleteCategory` 全部 `WHERE ... AND user_id = ?`，越权操作一律当「不存在」返回（不泄露存在性）。`server/_selftest.js` 还专门验证 userB 改/删不了 userA 的数据。**这是整个认证里最稳的一块。**
- 密码 bcrypt 哈希（cost=10）。
- 登录错误信息统一为「用户名或密码错误」（防内容枚举）。
- SQL 全参数化（`db.prepare().run()`），无注入面。
- 上传文件双校验（扩展名 + mimetype 严格锚定）。
- 所有受保护接口都挂了 `requireAuth`。
- `JWT_SECRET` 未设时有 `console.warn` 提示。

## 四、发现的问题（分级）

### 🔴 高 — JWT 密钥默认值（认证根基）

**位置**：`server/index.js:29`
```js
const JWT_SECRET = process.env.JWT_SECRET || 'candy-gallery-dev-secret-change-me-in-prod';
```
**影响**：密钥写死在源码里。生产环境一旦忘设 `JWT_SECRET`，就用这个公开默认值 → 任何读到源码的人可伪造合法 token 通过 `requireAuth`，认证形同虚设。`console.warn` 在生产日志里太容易被忽略。
**根因**：「默认值兜底」是为开发方便，但「静默回退到一个已知弱密钥」是认证反模式。

### 🟠 中 — `/uploads` 文件完全无鉴权

**位置**：`server/index.js:60`
```js
app.use('/uploads', express.static(path.join(__dirname, 'uploads')));
```
**影响**：所有上传的图片/视频不带 token 即可访问，filename（`${Date.now()}-${nanoid(6)}${ext}`，:181）的「不可猜」是唯一屏障。URL 一旦泄露（浏览器历史 / Referer / 日志 / 分享链接 / CDN 缓存），任何人拿到原图。**API 层按 `user_id` 隔离得很好，但文件层访问控制是空的——API 的越权防护被静态目录绕过了。**
**根因**：访问控制只在 DB/API 层做，没下沉到文件层。

### 🟠 中低 — 登录时序侧信道（用户名枚举）

**位置**：`server/index.js:121-124`
```js
const user = db.findUserByUsername(...);
if (!user) return res.status(401)...        // 用户不存在：直接返回，不跑 bcrypt
const ok = await bcrypt.compare(...);        // 用户存在但密码错：跑 bcrypt（慢）
```
**影响**：错误信息虽统一，但两条路径响应时间差几十毫秒（bcrypt cost=10 ≈ 50ms）。攻击者测响应时间即可判断用户名是否存在，统一错误信息的防护被时序差抵消。
**根因**：用户不存在时跳过了哈希运算。

### 🟠 中低 — 登录/注册无速率限制

**位置**：`/api/auth/login`、`/api/auth/register`
**影响**：无 rate limit / 失败锁定。bcrypt 提供一定保护，但无限制的慢速爆破或枚举可行。
**注**：关闭公开注册后（决策 4），此威胁面大幅缩小——详见决策记录。

### 🟡 低 — 其他

| 问题 | 位置 | 影响 |
|---|---|---|
| 前端 `isLoggedIn` 只看本地有无 token，不校验有效性 | `auth.js:14`、`router/index.js:20` | 过期 token 刷新后短暂放行，靠 401 自愈，会闪页。UX，非安全 |
| 后端用户名无格式/长度校验（只 trim） | `index.js:90-96` | 直接打 API 可注册超长/怪字符用户名，造脏数据 |
| 500 直接返回 `err.message` | `index.js:111,261,...` | 泄露内部错误细节 |
| token 存 localStorage | `auth.js:9,48` | XSS 可偷 token。本项目无 `v-html`、字段走 Vue 默认转义，XSS 面小 |
| JWT 无服务端失效 | 全局 | 登出只删前端 token，泄露后剩余有效期内可用 |
| `cors()` 全开 | `index.js:54` | Bearer 不随跨域自动携带，CSRF 低；但允许任意源带 token 读响应 |

## 五、修复决策（grilling 共识）

### 核心决策

| # | 决策点 | 选定 | 理由 |
|---|---|---|---|
| 1 | 部署形态 | 公网·私有图库 | 项目根决策，决定威胁模型（见第一节） |
| 2 | JWT 密钥 | **fail-closed**：未设 `JWT_SECRET` 进程 `throw` 退出 | 公网私有图库，认证根基不能赌「开发者记得设 env」；fail-closed 是唯一机械保证 |
| 3 | 文件鉴权 | **签名 URL**：保留 Bearer，HMAC 短期签名，替代裸 `/uploads` | Bearer 已全跑通，动它风险大；签名 URL 只动文件访问层。约束：`<img src>` 无法带 Authorization header，所以纯 Bearer 无法直接保护图片 |
| 4 | 注册策略 | **关闭公开注册**（`REG_OPEN=false`）+ CLI 建号 | 「自己+受邀者」与开放注册矛盾；关闭是最小暴露面 + 最小改动 |
| 5 | 爆破防护 | **只拉平登录时序**（用户不存在时补 dummy bcrypt） | 关闭注册后攻击者无用户名清单，时序拉平堵死枚举，bcrypt 拖慢爆破。不上限流/锁定 |
| 6 | token 失效 | **过期缩到 2 天**（`JWT_EXPIRES_IN='2d'`） | XSS 面小（Vue 转义），token 泄露是低概率事件；一行配置把泄露窗口从 7 天砍到 2 天，性价比最高 |

### 附带默认（小项，实现时按此处理）

- **签名 URL 细节**：`HMAC-SHA256(JWT_SECRET, filename|exp)`，过期 **1 小时**（覆盖「列表拉取 → 图片实际加载」最大间隔，太短会导致懒加载的图过期 401），覆盖原图 + 缩略图 + 视频；`getImages` / `getCategories` 返回时签发；视频 Range 请求同样验签。
- **CORS**：从 `cors()` 全开收紧为**只允许前端域名**（`cors({ origin: process.env.CORS_ORIGIN })`）。
- **500 错误**：不再回 `err.message`，返回通用「服务器错误」，细节进日志。
- **后端用户名校验**：补 `/^[a-zA-Z0-9_一-龥]{2,20}$/`，与前端一致。

## 六、grill 过程中的修正（增量价值）

> 这部分记录 grilling 如何改变了最初的建议，避免日后重复走弯路。

1. **关注册 → 爆破面缩小 → rate limit 降级**
   最初分析报告把「加 rate limit」列为建议项。grill 到第 4 问关闭公开注册后，攻击者拿不到有效用户名清单（不能注册探测、login 不返回用户列表），配合第 5 问时序拉平，枚举被堵死、bcrypt 拖慢爆破，rate limit 边际收益已很低 → 降级为「只拉时序」（ponytail，不堆机制）。

2. **否掉 refresh token / token 版本号**
   第 6 问评估 token 失效时，考虑过 refresh token（标准但重）和 token 版本号（中等工作量）。因项目无 `v-html`、字段走 Vue 默认转义，XSS 面小，token 泄露是低概率事件 → 否掉重机制，选最便宜的「缩短过期」。

## 七、明确不做的事（取舍记录）

> 记录「为什么不做」，避免日后重复讨论。

| 不做的事 | 理由 |
|---|---|
| 改 httpOnly cookie 认证 | 更彻底（防 XSS 偷 token + 图片可 requireAuth 流式），但要改认证架构 + 加 CSRF 防护 + 前后端都动。签名 URL 已解决文件鉴权，性价比不足 |
| 登录失败 rate limit / 账号锁定 | 关闭注册后爆破面小；账号锁定在小圈子场景易误锁自己；rate limit 重启计数清零、NAT 误伤 |
| refresh token / 服务端 token 黑名单 / token 版本号 | XSS 面小，token 泄露低概率；机制重，性价比低。用「过期 2 天」被动降低窗口即可 |
| 后端用户名加密存储 | 用户名不是高敏感字段（密码已 bcrypt），隔离靠 user_id，不需要 |

## 十、二轮 grilling 补充决策（第 7–12 问）

一轮落地后，对剩余侧枝又做了一轮 grilling，决策如下：

| # | 决策点 | 选定 | 理由 |
|---|---|---|---|
| 7 | 密码强度 | **≥8 位 + 字母数字**（前后端 + CLI 同步） | 公网暴露基线；假设用户名泄露后密码是最后防线，6 位会被字典一次击中 |
| 8 | 签名 URL 密钥 | **独立 `URL_SIGN_SECRET`**（fail-closed） | 职责分离（纵深防御）；改动不大 |
| 9 | CSP | **不加**，靠 Vue 转义 | Vue 默认转义压低 XSS 面；CSP 在部署层配 + 要白名单字体/iconify，配错白屏 |
| 10 | HTTPS | **在 NPM 配**（Force SSL + HSTS） | 反代架构下代码强制 HTTPS 会搞坏（Node 收到的是内网 HTTP） |
| 11 | 调试脚本 | **删** `_pw_check`/`_check`/`_db_check`，**留** `_selftest`/`_auth_selftest` | 一次性调试脚本无留存价值（`_pw_check` 含硬编码 hash）；selftest 是回归测试，无私密数据 |
| 12 | 存储配额 | **本地存储启用**（`UPLOAD_QUOTA_MB`，0=不限），**OSS 不限** | 本地磁盘稀缺要保护；OSS 弹性容量 + 按量付费，应用层配额无意义 |

### NPM（Nginx Proxy Manager）部署要点
- Proxy Host → Forward 到 Node 的 3000 端口
- **SSL 标签**：Let's Encrypt 证书 + 勾 **Force SSL** + **HTTP/2 Support** + **HSTS**
- **同域转发** `/`、`/api`、`/uploads` 到 Node（保证签名 URL 相对路径同源生效）
- HTTP→HTTPS 重定向由 NPM 的 Force SSL 自动处理
