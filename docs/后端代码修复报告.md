## 二、致命 Bug 修复（#1）

### 现象
用户上传图片成功后，画廊里**看不到自己刚传的图**。

### 根因
`images` 表有 `user_id` 字段，但 `addImages()` 的 INSERT 语句**漏写了 `user_id` 列**：

```js
// 修复前（db.js）
const stmt = db.prepare(
  'INSERT INTO images (id, filename, original_name, url, size, category_id, uploaded_at) VALUES (?, ?, ?, ?, ?, ?, ?)'
  //                                                                  ↑ 少了 user_id，共 7 列
);
```

而 `index.js` 构造的 item 明明带了 `userId`，却没被写进库。结果所有新图的 `user_id` 都是 `NULL`。
查询时 `getImages()` 用 `WHERE user_id = ?` 过滤，`NULL` 永远匹配不上 → **上传成功但查不到**，连带 `deleteImage` / `updateImageName`（都按 `id AND user_id` 查）也一起失效。

### 修复
INSERT 补上 `user_id` 列与占位符：

```js
// 修复后（db.js）
const stmt = db.prepare(
  'INSERT INTO images (id, filename, original_name, url, size, category_id, user_id, uploaded_at) VALUES (?, ?, ?, ?, ?, ?, ?, ?)'
);
// ...
stmt.run(item.id, item.filename, item.originalName, item.url, item.size,
         item.categoryId, item.userId, item.uploadedAt || Date.now());
//                       ^^^^^^^^^^ 现在写入归属
```

### 验证
回归自检 `server/_selftest.js` 第一组：插入 2 张图 → `WHERE user_id=?` 查到 2 张 ✅，跨用户查到 0 张 ✅。

## 三、安全越权修复（#2）

### 现象
任意登录用户 A，只要猜到用户 B 的 `categoryId`，就能**改名、改颜色、甚至删除** B 的分类。还能改全局 `cat_default`，污染所有用户的默认分类显示。

### 根因
`PUT /api/categories/:id` 与 `DELETE /api/categories/:id` 调 db 时**没传 `userId`**，db 层 SQL 也只按 `id` 过滤：

```js
// 修复前
// index.js
db.updateCategory(req.params.id, req.body)   // 没传 req.user.id
db.deleteCategory(req.params.id)             // 没传 req.user.id
// db.js
'SELECT * FROM categories WHERE id = ?'      // 没有 user_id 限制
'UPDATE categories SET ... WHERE id = ?'     // 同上
```

对比同文件 `updateImageName` / `deleteImage` 都正确带了 `AND user_id = ?`——本处是遗漏。

### 修复
db 层两个函数加 `userId` 参数，SQL 全部补 `AND user_id = ?`；index 层传入 `req.user.id`。越权访问统一返回 404（不泄露分类是否存在）：

```js
// 修复后（db.js）
function updateCategory(id, { name, color }, userId) {
  const cat = db.prepare('SELECT * FROM categories WHERE id = ? AND user_id = ?').get(id, userId);
  if (!cat) return null;                       // 不是自己的 → 当不存在
  // ...
  db.prepare('UPDATE categories SET name=?, color=? WHERE id=? AND user_id=?').run(...);
}
function deleteCategory(id, userId) {
  const cat = db.prepare('SELECT * FROM categories WHERE id = ? AND user_id = ?').get(id, userId);
  if (!cat) return null;                       // 同上
  // ... HAS_IMAGES 检查保留 ...
  return db.prepare('DELETE FROM categories WHERE id=? AND user_id=?').run(id, userId).changes > 0;
}
```

附带收益：全局 `cat_default`（`user_id IS NULL`）普通用户再也匹配不到，**无需再单独做字符串黑名单**，原 `PROTECTED` 分支已移除。

### 验证
回归自检第二、三组：userB 改/删 userA 分类 `changes=0` ✅，userA 改自己 `changes=1` ✅。

## 四、其他修复（#3 ~ #6）

### #3 重复「未分类」分类
**根因**：`init()` 建了全局 `cat_default`（`user_id IS NULL`），`ensureDefaultCategory()` 又给每用户建私有「未分类」，而 `getCategories` 用 `WHERE user_id=? OR user_id IS NULL`，于是同一用户拿到**两条** `name='未分类'`。

**修复**：`getCategories` / `getUserCategoryIds` 改为「先查用户私有分类；仅当用户没有任何分类时，才回退到全局兜底」。正常用户（注册/登录时已补私有分类）只看到自己那一份，重复消失。

### #4 事务写法
**根因**：`addImages` 用手写 `BEGIN/COMMIT/ROLLBACK`，注释写「node:sqlite 没有 transaction()」——但同文件 `init()` 就用了 `db.transaction()`，注释自相矛盾。

**修复**：改用 `db.transaction(() => {...})()`，自动回滚，与 `init()` 一致。

### #5 multer 文件类型校验
**根因**：`/jpeg|jpg|png|gif|webp/` 无锚定，是子串匹配，`text/jpeg`、`image/pngx`、`application/x-jpg` 等都能通过。

**修复**：改为锚定正则：
```js
const okExt  = /\.(jpe?g|png|gif|webp)$/i.test(file.originalname);
const okMime = /^image\/(jpeg|png|gif|webp)$/.test(file.mimetype);
```

### #6 多文件 originalName 兼容
**根因**：后端按 `upload.array('files', 20)` 支持多文件，却把 `req.body.originalName` 当单值。若一次提交多文件，要么多个文件共用一个名，要么 `originalName` 变数组时 `.trim()` 直接抛错。

**修复**：按文件索引取（数组形态按 `rawNames[i]`，单值形态共用，缺失则回退 `latin1→utf8` 解码）。

> 注：当前前端是**逐文件**单独发请求，此 bug 本不会触发；本次为后端按多文件设计做防御性加固。

## 五、未自动修改的项（需决策）

这两项**未在本次提交中改代码**，原因与建议如下：

### 1. JWT_SECRET 默认硬编码（已加告警，未阻断）
- 现状：`JWT_SECRET` 缺省值为 `'candy-gallery-dev-secret-change-me-in-prod'`，生产若不设环境变量，攻击者可伪造任意用户 token。
- 已做：启动时若未设 `JWT_SECRET`，打印醒目告警。
- **建议**：生产部署通过环境变量注入随机密钥；如需更严格，可改为「未设则拒绝启动」（dev 也设本地值即可）。

### 2. `/uploads` 静态资源无鉴权（架构问题，未改）
- 现状：`app.use('/uploads', express.static(...))` 任何人凭文件名即可下载任意用户图片。文件名 `时间戳-nanoid(6)` 有一定不可猜性，但并非真正鉴权。
- **未改原因**：前端用 `<img :src="url">` 直接引用图片，`<img>` 标签**无法携带 `Authorization` 头**。若直接给 `/uploads` 加 `requireAuth` 中间件，所有图片加载都会 401，前端会全线崩溃。这是架构层改动，需要换方案，不应在本次「修 bug」里顺带做。
- **可选方案**（任选其一，需你拍板后再动）：
  1. **签名 URL**：图片地址带短期 token 参数，`/uploads/:file?sig=...` 由后端校验。改动小，前端只改 URL 拼装。
  2. **改用 Cookie 鉴权**：登录下发 httpOnly cookie，`<img>` 会自动带，`/uploads` 加中间件即可。涉及鉴权体系切换。
  3. **中转下载接口**：`GET /api/images/:id/download` 走 `requireAuth`，用 `res.download` 流式输出。前端 `<img>` 改指向该接口。最干净但要改前端图片源。

## 六、数据遗留情况（已核实真实库）

查询 `server/db.sqlite` 实际状态：

| 项 | 数量 |
|---|---|
| `images` 总数 | 0 |
| 孤儿图（`user_id IS NULL`） | 0 |
| `users` | 1 |
| 全局分类（`user_id IS NULL`） | 1（`cat_default`） |
| 用户私有分类 | 1 |

**结论**：
- 图片表为空，**没有历史孤儿图需要数据迁移**（#1 的 bug 没留下脏数据）。
- 全局 `cat_default` 仍存在，但修复后对已注册用户不再返回（用户有私有分类，不再回退全局），已**惰性无害**。若想彻底清掉：
  ```sql
  -- 可选：删除无主全局分类（确认无 images 引用，当前库无引用）
  DELETE FROM categories WHERE id = 'cat_default' AND user_id IS NULL
    AND id NOT IN (SELECT category_id FROM images);
  ```
- `server/uploads/` 下有若干 png 是早期测试残留（库中无对应记录），可手动清理，不影响功能。
